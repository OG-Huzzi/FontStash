How should font data get into the app?

Three approaches for Phase 1 — Google Fonts only (~1,500 families). The choice affects build time, bundle size, and how search/filter feel.

A

Committed JSON + client-side Fuse.js (Recommended)

A standalone build script pulls the full Google Fonts catalog once, normalizes to your schema, runs the LLM mood-tagger, and writes a single fonts.json (~1,500 entries, ~600KB gzipped) committed to the repo. At build time, Next.js statically generates /font/[slug] pages from it. The homepage hydrates the JSON in the browser and builds a Fuse.js index in memory once. Search & filters are fully client-side, instant, no API calls.

Pros

  • Truly static — no serverless function, no runtime API calls, deployable to any static host
  • Search is instant (<50ms), works offline once loaded
  • SEO pages generate at build, not request time
  • Repo is self-contained — rebuild only when refreshing the catalog

Cons

  • ~600KB JSON shipped to client (acceptable, loads once, cached)
  • Font catalog freshness requires re-running the pipeline script (manual refresh)
B

Edge API route fetches Google at runtime

No committed JSON. A Next.js edge function fetches the Google Fonts catalog on the first request and caches it at the edge. Fuse.js index builds server-side per request (or edge-cached). Homepage calls this endpoint.

Pros

  • Catalog is always fresh, no manual refresh
  • Nothing large committed to repo

Cons

  • No longer "fully static" — contradicts your no-backend constraint
  • Cold-start latency on first request, edge cache complexity
  • SEO pages can't be statically generated from runtime data
  • Mood tagging can't happen at runtime (LLM call per request = cost + latency)
C

Hybrid: committed JSON, but lazy-chunked

Same as A, but the JSON is split into ~30 chunks (~50 fonts each) loaded on-demand as the user scrolls or filters. Fuse.js index built incrementally. Initial payload drops to ~40KB.

Pros

  • Smallest initial payload (~40KB)
  • Best first-load performance metric

Cons

  • Fuse.js can't search fonts that haven't been loaded yet — typing a query may miss fonts in unloaded chunks
  • Significant complexity (chunk loading, partial index merging, sort/filter across chunks)
  • "Search 3,000+ fonts" promise breaks if search is scoped to loaded chunks only
  • Over-engineered for 600KB of data

My recommendation is A — it matches your "fully static, no backend" constraint exactly, gives instant client-side search, and 600KB gzipped is a one-time cost that loads once and caches forever. Click to select, or tell me in the terminal.
